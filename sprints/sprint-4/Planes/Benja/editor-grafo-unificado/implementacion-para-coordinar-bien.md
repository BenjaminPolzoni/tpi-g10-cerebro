## 3. Fuera de este change (historias aparte, empiezan por el back)

- **F9 — Tipos de relación creados por el profesor** y relaciones informativas en el editor (`recommends`, `belongs_to`, `part_of`, `related_to`). Hoy el editor no las toca (Enmienda 1).

- **Endpoint transaccional crear nodo + regla**: hoy son dos llamadas (`POST .../nodes` y `PATCH .../rules`) y el front reporta fallo parcial. Si molesta en la práctica, un endpoint atómico lo resuelve.

## 6. Brechas de back para la iteración 2 (2026-10-29)

La exploración de `src/app/features/roadmap/data-access/roadmap/roadmap.store.ts`, `roadmap-http/http-roadmap.adapter.ts` y los contratos anotados en `design.md` muestra que la mayor parte del alcance nuevo no pide un endpoint de requisitos nuevo. Cerrar/coordinar estos puntos antes de prometer consistencia transaccional:

- [ ] **No hay transacción para alta + requisitos.** La creación del nodo (`POST .../sections/{sectionId}/nodes`) y su regla (`PATCH .../nodes/{id}/rules`) son dos mutaciones. Si la primera confirma y la segunda rechaza/falla por red, el nodo existe sin requisitos; el front debe dejarlo visible y reintentar solo la regla. Si se necesita atomicidad real, back debe proponer endpoint idempotente que acepte entidad + árbol y defina rollback/errores; es una mejora opcional, no requisito para guardar multi-leaf.
- [ ] **Verificar shape/respuesta de alta por endpoint y despliegue.** Adapter tipa `ApiResponse<BackendNodeResponse>`/`BackendSectionResponse`; store actual abstrae create como `void` salvo id o callback de entidad, y ejecuta `reload()` sin esperar que termine antes de notificar caller. Confirmar que la respuesta contiene id y orden normalizado (`sortOrder`) para nodos, secciones y zonas. Si no trae campos suficientes, el front puede releer por id tras 2xx; pedir campo nuevo solo si no es posible resolverlo de modo confiable. No agregar entidad optimista.
- [ ] **Persistencia del orden de subsecciones.** `RoadmapStore.reorderSections` y el contrato de orden documentado cubren unidades; verificar con `tpi-roadmap` que POST/PATCH de orden acepta siblings de subsección. Si no, abrir operación backend equivalente (sortOrder por parent) y rechazar/hide el reorder hasta disponer de ella; el front no debe anunciar éxito basado solo en orden local.
- [ ] **Contrato de elegibilidad multifuente y hoja SECTION/NODE por owner.** El código revisado indica que PATCH de reglas de sección acepta árbol con NODE externo elegible y SECTION, también para subsecciones; los contratos de nodo usan `saveRules`. Confirmar por tests HTTP de aceptación/rechazo (incluidos NODE+SECTION juntos, AND/OR, subsección, oculto/eliminado y ciclo/contención) y smoke test de la versión desplegada antes de declarar paridad. El front hace una escritura de árbol completo por owner, de modo que no se requiere endpoint bulk solo por seleccionar varias fuentes.
- [ ] **Regla section→section y evaluación AND/OR entre unidades.** Confirmar que API y evaluador de progreso preservan hojas de SECTION en árbol (sin perderlas en la proyección flat) para unidad y subsección, y que el significado de AND = todas / OR = cualquiera es idéntico en editor, General y alumno. Si hay divergencia, falta en back un test de contrato/integración y/o corrección de persistencia/evaluación.
- [ ] **Relaciones DEC-018 no son requisitos.** `/roadmaps/{id}/relations` soporta relaciones tipadas (DEC-018); el `REQUIRES` del grafo debe seguir guardándose mediante `PATCH /nodes/{id}/rules` o `/sections/{id}/rules`. No mandar varios source-target a `relations` esperando AND/OR: ese endpoint no representa el árbol de reglas.
- [ ] **Compatibilidad con edición concurrente/idempotencia.** No hay confirmado un idempotency key/version de mutación de reglas/alta. El front bloquea doble submit y relee tras éxito/foco; confirmar si POST duplicado tras timeout ambiguo puede producir nodos duplicados, y documentar mitigación (idempotency key/lookup) si el riesgo requiere garantía del back.
